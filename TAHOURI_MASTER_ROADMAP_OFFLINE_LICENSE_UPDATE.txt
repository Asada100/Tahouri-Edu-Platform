========================================
2. OFFLINE-FIRST PRINCIPLE
========================================

Normal educational use must work without Internet.

The installed application contains:
- educational content
- games
- images/assets
- engines
- local progress
- local profile data
- local settings
- locally cached license entitlement

Internet is optional for normal learning.

Internet is required/used only when available for online control-plane functions such as:
- first license activation/verification
- optional license refresh/revocation check
- update availability check
- downloading an update
- future online Interaction features
- future optional synchronization

If Internet is unavailable:
- the application must continue working according to the locally valid license
- no ordinary game/content screen should fail because of missing Internet
- update checks should fail silently/non-disruptively

========================================
3. LICENSE ARCHITECTURE
========================================

Separate these concepts:

License != Code != Payment != Profile

License:
- annual educational entitlement
- tied to product/academic year
- server-issued
- locally verifiable after activation

Code:
- activation/gift mechanism
- random/unpredictable
- not hardcoded into the application
- stored server-side as a secure representation where appropriate

Payment:
- verified server-side through a payment gateway
- never trusted solely from a client redirect/result

Profile:
- existing Tahouri profile system remains separate
- no requirement to collect student names/personal identity for the licensing service

License should support:
- activation
- expiry
- renewal
- revocation
- extension
- status
- audit trail

========================================
4. ACADEMIC-YEAR EXPIRY
========================================

License validity is based on academic year, NOT 365 days from purchase.

Required business rule:
- license for academic year XXXX-XXXX+1 expires on 31 Shahrivar of the next academic year boundary
- exact server-side timezone must be defined as Iran Standard Time
- exact end timestamp must be server-controlled and documented
- the app must display the exact expiry date to the user

Example concept:
Academic year 1405-1406
=> valid through 1406/06/31
=> exact expiry timestamp defined centrally by the server.

The user should be informed:
- current license year
- exact expiry date
- whether renewal/next year's activation is available

========================================
5. OFFLINE LICENSE SECURITY
========================================

Preferred design:
- server creates a signed license/entitlement
- private signing key exists ONLY on server
- application contains only the public verification key
- application verifies signature locally
- license claims include at minimum:
  - licenseId
  - product/application identifier
  - academicYear
  - validUntil
  - optional device/install binding data if that policy is approved
  - version/schema information as needed

Never:
- embed private signing keys
- embed admin secrets
- embed gateway secrets
- trust a client-generated expiry date
- treat a plain editable JSON/license file as sufficient security

Need later design carefully for:
- local clock manipulation
- device changes
- reinstall behavior
- license transfer
- revocation when offline
- maximum offline grace/refresh policy, if any

Do not choose these policies until the product decision is made.

========================================

Existing Tahouri activation architecture is the starting point.

Known existing components include:

- licenseScreen.js

Do not replace them blindly.

Required final behavior:

========================================
8. GIFT SYSTEM
========================================

No fixed hardcoded gift code.

Admin panel must allow:
- create gift campaign/code
- securely generate random unique codes
- set product/grade if applicable
- set academic year
- set expiry
- set usage count
- activate/deactivate
- revoke
- inspect usage
- audit actions

Potential future extension:
- claim links/tokens
But this is not required for the first implementation.

Gift codes must not be stored as readable secrets in the client application.

========================================
9. PAYMENT SYSTEM
========================================

Required model:
Customer
 -> payment gateway
 -> server-side verification
 -> successful verified payment
 -> license issuance
 -> app activation

Rules:
- payment success must be verified server-side
- do not trust browser/client success messages
- gateway credentials stay on server
- do not expose a personal bank account number inside the app as a substitute for a payment system
- payment provider must be replaceable through an abstraction layer

Need later decide:
- automatic activation after verified payment
- code delivery inside the app
- both options

Preferred architecture should support both without changing the core app.

========================================
11. UPDATE SYSTEM
========================================

Home screen must support update notification.

When a new version is available:
- show a moving/animated text message on Home
- visual style should match the existing Dashboard message style
- message is informational, not aggressive advertising
- include:
  - "به‌روزرسانی"
  - "بعداً"

Example intent:
"نسخه جدید طهوری آماده است؛ برای دریافت امکانات و محتوای جدید، برنامه را به‌روزرسانی کنید."

If user selects "بعداً":
- close/dismiss the current update prompt
- application continues normally
- a future reminder may appear according to a non-annoying policy

If update succeeds:
- show a short thank-you/success message
- e.g. "به‌روزرسانی با موفقیت انجام شد؛ ممنون که همراه طهوری هستید."
- after a short delay return Home to its normal previous state

If update cannot be performed:
- do not block normal learning
- do not damage the current installation
- user can continue using the existing valid version

Update checks:
- only when Internet is available
- must fail safely when offline
- must not make the core application dependent on the update server

Update system must support:
- version manifest
- release metadata
- optional download
- version compatibility
- rollback-safe installation strategy where technically appropriate
- migration handling if data schema changes
- optional updates, not mandatory unless a critical/security reason is later approved

========================================
14. CHILD-SAFE COMMERCIAL MODEL
========================================

Tahouri is primarily cultural/educational.
Approximate product principle:
- 95% cultural/educational
- not an advertising platform

Do NOT make generic third-party advertising the core revenue model.

Reasons:
- target audience includes children
- uncontrolled ad networks can display inappropriate content
- ad content can be inconsistent with educational goals
- store policies for children add additional restrictions

Preferred alternatives:
1. annual educational license
2. Tahouri's own educational content/products
3. educational sponsorship
4. carefully controlled internal announcements

Internal announcements should be:
- educational
- product-related
- clearly distinguishable from lesson/game content
- non-invasive
