سند مرجع مسیر توسعه موتورهای طهوری
Tahouri Engine Development Roadmap
نسخه 1.1

وضعیت:
این سند مرجع اصلی ترتیب توسعه موتورهای آموزشی پروژه است.
در هر گفت‌وگوی جدید، مرحله توسعه باید با آخرین Commit پروژه تطبیق داده شود.
هدف سند این است که هنگام ساخت Activity جدید، تا حد امکان از موتور و قابلیت موجود استفاده شود و ساخت موتور جدید به حداقل برسد.

==================================================
1. اصل اصلی توسعه
==================================================

ترتیب تصمیم‌گیری برای هر قابلیت جدید:

ایده فعالیت
↓
بررسی موتورهای موجود
↓
بررسی Type / Mode / قابلیت موجود
↓
اگر لازم بود توسعه همان موتور
↓
اگر لازم بود Type / Mode جدید
↓
فقط در صورت ناتوانی واقعی معماری موجود، موتور جدید

در زمان ساخت بازی، ایده‌های جدید نباید به‌صورت خودکار باعث ساخت Engine جدید شوند.

یک قابلیت جدید ابتدا باید به‌عنوان «محتوا»، سپس «Type/Mode»، سپس «توسعه موتور موجود» بررسی شود.

==================================================
2. محدوده پروژه
==================================================

محدوده فعلی: پایه‌های اول تا ششم ابتدایی.
پیش‌دبستانی: پروژه آینده و فعلاً خارج از توسعه جاری.
متوسطه و دانشگاه: خارج از محدوده پروژه فعلی.

نکته:
این محدوده برای انتشار فعلی پروژه است، نه برای طراحی معماری موتورهای عمومی.
هر موتور عمومی که اکنون ساخته می‌شود باید در صورت امکان قابلیت توسعه برای پایه‌های پایین‌تر یا بالاتر را داشته باشد، بدون اینکه محدوده انتشار فعلی تغییر کند.

==================================================
3. موتورهای اصلی و ظرفیت آن‌ها
==================================================

1) Quiz Engine
وضعیت: فعال و آماده

کاربرد:
- سؤال چهارگزینه‌ای
- درست/غلط
- انتخاب تصویر
- انتخاب پاسخ
- سؤال همراه تصویر
- سؤال همراه صوت در صورت آماده بودن لایه صوت
- سنجش دانش و مفاهیم

اولویت: پایین؛ فقط تکمیل Typeهای موردنیاز.
قاعده: هر فعالیت سؤال‌محور ابتدا با Quiz بررسی شود.

--------------------------------------------------
2) Memory Engine
وضعیت: فعال و آماده

کاربرد:
- تصویر ↔ تصویر
- تصویر ↔ کلمه
- تصویر ↔ صوت
- عدد ↔ مقدار
- سؤال ↔ پاسخ
- حافظه توالی
- حافظه موقعیت

اولویت: متوسط.
قاعده: فعالیت‌هایی با هدف اصلی «به خاطر سپردن و بازیابی» ابتدا با Memory بررسی شوند.

--------------------------------------------------
3) Matching Engine
وضعیت: فعال و آماده

کاربرد:
- یک به یک
- چند مورد به یک مورد
- ارتباط مفهومی
- هم‌معنی
- متضاد
- تصویر ↔ کلمه
- صدا ↔ تصویر
- عدد ↔ مقدار
- شکل ↔ نام
- شیء ↔ کاربرد
- حیوان ↔ زیستگاه
- علت ↔ معلول
- سایر روابط دوطرفه

اولویت: خیلی بالا.
قاعده: برای روابط و تطبیق‌ها ابتدا Matching بررسی شود؛ موتور جدید ساخته نشود.

--------------------------------------------------
4) Classification Engine
وضعیت: فعال؛ نیازمند تکمیل ظرفیت

کاربرد:
- دسته‌بندی
- گروه‌بندی
- طبقه‌بندی تصویری
- طبقه‌بندی بر اساس ویژگی
- چند ویژگی
- انتخابی
- Drag & Drop
- Sorting در صورت پیاده‌سازی به‌عنوان Type/Mode
- فعالیت‌های چندمرحله‌ای

مورد مهم:
multiStageClassification باید به‌عنوان قابلیت رسمی موتور تکمیل و تست شود و دیگر فراموش نشود.

اولویت: بسیار بالا.

قاعده: Sorting تا حد امکان موتور مستقل نباشد و ابتدا به‌عنوان قابلیت Classification یا Puzzle بررسی شود.

--------------------------------------------------

- Visual Math

- Pattern

کاربردهای قابل توسعه:

- حل مسئله

- تجسم فضایی

اولویت: بسیار بالا.

قاعده:

توجه:

--------------------------------------------------

==================================================
4. Spatial — موتور/قابلیت عمومی تجسم و درک فضایی
==================================================

نام مفهومی:
Spatial = موتور تجسم و درک فضایی

وضعیت فعلی:
Spatial در معماری فعلی به‌صورت Type در Puzzle ساخته شده است.
Engine مستقل فعلاً ساخته نمی‌شود.

هدف:
Spatial نباید به یک سؤال خاص مثل «شکل را در خانه درست قرار بده» محدود شود.
هدف آن پوشش مجموعه‌ای از فعالیت‌های درک موقعیت، رابطه فضایی، شکل، جهت، تقارن، دوران، جابه‌جایی، تجسم و بازسازی است.

اصل مهم:
شبکه 3×3 یا فعالیت فعلی mathSpatial فقط یک نمونه از Spatial است و نباید به‌عنوان تعریف کل Spatial در نظر گرفته شود.

--------------------------------------------------
4.1) خانواده Match / Place — تطبیق و جای‌گذاری
--------------------------------------------------

کاربرد مناسب برای:
- پیش‌دبستان
- پایه اول
- پایه‌های پایین‌تر ابتدایی
- فعالیت‌های ساده‌تر پایه‌های بالاتر

نمونه فعالیت:
- صفحه بدون شبکه با چند جای مشخص
- نمایش هاله یا تصویر کم‌رنگ از محل صحیح
- برداشتن شیء و قرار دادن آن روی جای خودش
- تطبیق شکل با محل مناسب
- قرار دادن اشیاء بر اساس موقعیت نسبی
- قرار دادن چند شکل در یک تصویر

قانون طراحی:
در فعالیت‌های آموزشی کودک، مقصد نباید بی‌دلیل مخفی باشد.
اگر هدف فعالیت «تطبیق و جای‌گذاری» است، می‌توان محل صحیح را با هاله، سایه، طرح کم‌رنگ یا Slot مشخص کرد.

--------------------------------------------------
4.2) خانواده Find — پیدا کردن شکل
--------------------------------------------------

کاربرد:
- پیدا کردن شکل ساده پنهان در تصویر
- تشخیص یک یا چند شکل در یک تصویر
- پیدا کردن شکل‌های هم‌شکل
- پیدا کردن اجزای یک شکل در تصویر

سطح ساده:
- شکل‌ها کاملاً قابل تشخیص باشند.
- تعداد شکل‌های پنهان کم باشد.
- هم‌پوشانی و پیچیدگی محدود باشد.

سطح پیشرفته:
- شکل داخل ترکیب پیچیده‌تر قرار گیرد.
- چند شکل در یک تصویر وجود داشته باشد.
- شکل‌ها بخشی از یک تصویر بزرگ‌تر باشند.

این خانواده نباید با فعالیت‌های صرفاً حافظه‌ای اشتباه گرفته شود؛ هدف اصلی باید ادراک و تشخیص فضایی/دیداری باشد.

--------------------------------------------------
4.3) خانواده Arrange / Build — جابه‌جایی و ساخت شکل
--------------------------------------------------

کاربرد:
- جابه‌جایی قطعات برای ساخت یک شکل
- کامل کردن تصویر با قطعات
- قرار دادن چند قطعه در جای درست
- بازسازی یک شکل نمونه
- ترکیب چند شکل ساده برای ساخت شکل بزرگ‌تر
- Tangram-like activities در صورت نیاز محتوایی

تعامل:
- Mouse Drag
- Touch Drag

اصل:
انتخاب حروف یا کلیک ساده، تعامل اصلی این خانواده نیست؛ حرکت دادن قطعه باید بخش اصلی تجربه باشد.

--------------------------------------------------
4.4) خانواده Grid — شبکه و موقعیت
--------------------------------------------------

کاربرد:
- قرار دادن شکل در مختصات مناسب
- حرکت دادن شکل روی شبکه
- پیدا کردن خانه صحیح
- دنبال کردن مسیر
- ساختن شکل روی شبکه
- انتقال شکل از یک موقعیت به موقعیت دیگر
- مقایسه موقعیت‌ها
- استفاده از مختصات در صورت تناسب با پایه

Grid می‌تواند از شبکه ساده برای پایه‌های پایین‌تر تا شبکه شطرنجی دقیق برای پایه‌های بالاتر توسعه یابد.

--------------------------------------------------
4.5) خانواده Direction / Path — جهت و مسیر
--------------------------------------------------

کاربرد:
- بالا / پایین / چپ / راست
- مسیر‌یابی
- حرکت در شبکه
- دنبال کردن دستورهای حرکتی
- پیدا کردن مسیر صحیح
- ترکیب چند حرکت
- مسیرهای مستقیم و در صورت نیاز مسیرهای پیچیده‌تر

این خانواده می‌تواند با Grid ترکیب شود و الزاماً Type مستقل نباشد.

--------------------------------------------------
4.6) خانواده Symmetry — تقارن
--------------------------------------------------

کاربرد:
- تشخیص شکل قرینه
- کامل کردن نیمه دیگر شکل
- ساختن نیمه قرینه با Drag
- قرار دادن خانه‌های قرینه روی شبکه
- تشخیص محور تقارن
- ساخت شکل متقارن
- بررسی درستی تقارن

سطح ساده:
تقارن تصویری و کامل کردن نیمه شکل.

سطح بالاتر:
تقارن روی شبکه و نسبت به محور مشخص.

نکته:
تقارن باید یکی از Modeهای اصلی Spatial باشد، نه یک موتور جداگانه.

--------------------------------------------------
4.7) خانواده Transform — انتقال، چرخش و دوران
--------------------------------------------------

کاربرد:
- انتقال شکل
- چرخش شکل
- دوران 90 درجه
- دوران 180 درجه
- دوران 270 درجه
- انتخاب نتیجه صحیح دوران
- انجام دوران با دکمه
- انجام دوران با Drag/Touch در صورت مناسب بودن UI
- مقایسه شکل قبل و بعد از تبدیل

در فعالیت‌های آموزشی می‌توان دو شیوه ارائه کرد:
1. دوران با کنترل‌های مشخص
2. دوران تعاملی با حرکت کاربر

هدف آموزشی باید تعیین کند کدام روش استفاده شود.

--------------------------------------------------
4.8) خانواده Hidden / Embedded Shapes — اشکال پنهان و درهم‌رفته
--------------------------------------------------

کاربرد:
- یافتن شکل داخل یک تصویر
- تشخیص شکل ساخته‌شده از چند خط
- پیدا کردن چند شکل ساده در یک ترکیب
- تشخیص اجزای شکل
- جدا کردن شکل هدف از شکل‌های مزاحم

این خانواده به‌خصوص برای فعالیت‌های دیداری پایه‌های پایین‌تر مناسب است.

--------------------------------------------------
4.9) خانواده 3D — تجسم سه‌بعدی
--------------------------------------------------

کاربرد:
- تشخیص جسم سه‌بعدی
- چرخاندن جسم
- مشاهده جسم از زاویه دیگر
- تشخیص نمای مناسب
- تطبیق جسم با تصویر/نما
- ساخت یا بازسازی ساده جسم از قطعات
- شمارش یا تشخیص اجزای قابل مشاهده در فعالیت‌های مناسب
- تجسم تغییر وضعیت جسم

این خانواده برای پایه‌های بالاتر اهمیت بیشتری پیدا می‌کند.

اصل معماری:
3D در صورت نیاز می‌تواند یک Renderer/Interaction Layer متفاوت داشته باشد، اما نباید صرفاً به دلیل سه‌بعدی بودن به‌صورت خودکار Engine آموزشی مستقل ایجاد شود.

--------------------------------------------------
4.10) خانواده View / Projection — نما و تجسم
--------------------------------------------------

کاربرد:
- تشخیص نمای روبه‌رو
- تشخیص نمای بالا
- تشخیص نمای جانبی
- ارتباط جسم با نماهای آن
- انتخاب تصویری که با جسم داده‌شده مطابقت دارد
- بازسازی ذهنی جسم از چند نما

این بخش مخصوصاً برای فعالیت‌های تجسم فضایی پایه‌های بالاتر اهمیت دارد.

--------------------------------------------------
4.11) خانواده Rotation in 3D — دوران سه‌بعدی
--------------------------------------------------

کاربرد:
- چرخاندن جسم در فضای سه‌بعدی
- مشاهده تغییر نمای جسم
- تطبیق جسم دوران‌یافته با پاسخ
- انتخاب زاویه درست
- مقایسه وضعیت اولیه و نهایی

این قابلیت باید در صورت نیاز روی زیرساخت 3D ساخته شود و با Rotation دوبعدی اشتباه نشود.

--------------------------------------------------
4.12) خانواده Composite Spatial — ترکیبی
--------------------------------------------------

در فعالیت‌های پیشرفته می‌توان چند قابلیت Spatial را ترکیب کرد:

- Grid + Symmetry
- Grid + Rotation
- Arrange + Symmetry
- Arrange + Rotation
- Hidden Shape + Find
- 3D + Rotation
- 3D + View
- Path + Direction
- Arrange + Grid
- Transform + Grid

ترکیب Modeها باید فقط زمانی انجام شود که هدف آموزشی روشن باشد؛ پیچیده کردن بازی به‌خودی‌خود هدف نیست.

==================================================
4.13) سطح‌بندی Spatial بر اساس سن و پایه
==================================================

Spatial یک مجموعه ثابت از بازی‌ها نیست.
محتوا، اندازه صفحه، تعداد قطعات، میزان راهنمایی و پیچیدگی تعامل باید با پایه تغییر کند.

پایه‌های پایین:
- اشیای بزرگ و قابل تشخیص
- تعداد کم قطعات
- مقصدهای مشخص
- هاله و راهنمای دیداری
- Drag & Drop ساده
- جهت‌های اصلی
- تقارن ساده
- شکل‌های آشنا

پایه‌های میانی:
- شبکه
- چند قطعه
- مسیر
- تقارن
- جابه‌جایی
- دوران ساده
- ترکیب چند رابطه فضایی

پایه‌های بالاتر:
- شبکه دقیق‌تر
- دوران و تبدیل
- تقارن پیچیده‌تر
- نماها
- تجسم سه‌بعدی
- چرخش سه‌بعدی
- ترکیب چند تبدیل

این سطح‌بندی «قفل معماری» نیست؛ هر Activity بر اساس هدف آموزشی خودش Mode و سطح مناسب را انتخاب می‌کند.

==================================================
4.14) کاربردهای بین‌درسی Spatial
==================================================

Spatial در درجه اول برای ریاضی مناسب است، اما محدود به ریاضی نیست.

ریاضی:
- شکل و فضا
- تقارن
- دوران
- انتقال
- موقعیت
- شبکه
- مسیر
- تجسم سه‌بعدی
- نماها
- الگوهای فضایی

علوم:
- ارتباط فضایی اجزای شکل‌ها
- تشخیص موقعیت اجزا
- مدل‌های ساده و ساختارها در صورت تناسب محتوایی

سایر دروس:
فقط در صورت وجود هدف آموزشی واقعی؛ Spatial نباید صرفاً برای تزئین یک فعالیت استفاده شود.

==================================================
4.15) قواعد UI و Interaction برای Spatial
==================================================

قابلیت‌های عمومی زیر Engine مستقل نیستند:

- Mouse Drag
- Touch Drag
- Pointer Events
- Connection Line
- Ghost / Target Hint
- Hint
- Feedback
- Animation
- Timer
- Reset
- Undo در صورت نیاز
- Zoom در فعالیت‌های مناسب
- کنترل چرخش

این‌ها باید تا حد امکان به‌صورت قابلیت‌های مشترک UI/Interaction پیاده‌سازی شوند.

اصل مهم:
اگر دانش‌آموز باید «شکل را جابه‌جا کند»، تعامل باید طبیعی باشد؛ کلیک‌های غیرضروری و انتخاب‌های چندمرحله‌ای نباید جای حرکت واقعی را بگیرند.

==================================================
4.16) وضعیت فعلی Spatial
==================================================

Spatial Type در Puzzle ایجاد شده است.

نمونه فعلی:
mathSpatial

Mode فعلی:
place

نمونه فعلی:
قرار دادن شکل‌ها در محل صحیح.

وضعیت:
[TESTING]

توجه:
نمونه فعلی فقط برای اثبات Interaction است و تعریف نهایی Spatial محسوب نمی‌شود.

مرحله بعدی Spatial:
1. تأیید UX فعلی.
2. استخراج Modeهای لازم از محتوای واقعی کتاب‌های درسی.
3. جلوگیری از ساخت Modeهای غیرضروری.
4. طراحی Schema مشترک Spatial.
5. توسعه Modeها به‌ترتیب ارزش آموزشی.
6. تست با Activity واقعی در پایه‌های مختلف.
7. ثبت وضعیت هر Mode در همین سند.

تا قبل از این بررسی، ساخت Engine مستقل Spatial ممنوع است.

==================================================
9. قانون جلوگیری از فراموشی
==================================================

هیچ قابلیت شناخته‌شده‌ای نباید به دلیل درگیری با خطای دیگری فراموش شود.

هر قابلیت نیمه‌کاره باید یکی از این وضعیت‌ها را داشته باشد:

[ACTIVE] در حال توسعه
[READY] آماده استفاده
[TESTING] در حال تست
[BLOCKED] به دلیل مشخص متوقف
[RESERVED] برای مرحله آینده
[DEPRECATED] دیگر مورد استفاده نیست

multiStageClassification باید همیشه وضعیت مشخص داشته باشد.

Spatial نیز باید برای هر Mode وضعیت مشخص داشته باشد و Modeهای پیشنهادی بدون نیاز واقعی به کد تبدیل نشوند.

==================================================
10. قانون شروع هر Activity جدید
==================================================

1. هدف آموزشی مشخص شود.
2. موتور مناسب انتخاب شود.
3. Type/Mode موجود بررسی شود.
4. اگر وجود دارد، همان استفاده شود.
5. اگر ناقص است، همان Type توسعه داده شود.
6. اگر وجود ندارد، Type جدید بررسی شود.
7. فقط اگر هیچ موتور موجود مناسب نبود، پیشنهاد Engine جدید مطرح شود.

ایده جدید مساوی موتور جدید نیست.

==================================================
11. قانون تصمیم‌گیری درباره Engine جدید
==================================================

ساخت Engine جدید فقط وقتی مجاز است که:
- چند Activity واقعی به آن نیاز داشته باشند؛
- موتورهای موجود نتوانند نیاز را پوشش دهند؛
- ساخت Type جدید در موتور موجود کافی نباشد؛
- افزودن قابلیت به موتور موجود باعث خراب شدن مسئولیت آن موتور نشود؛
- معماری فعلی حفظ شود.

==================================================
12. قانون استفاده از منابع آموزشی واقعی
==================================================

وقتی یک قابلیت قرار است برای چند پایه استفاده شود، ابتدا نمونه‌های واقعی کتاب‌های درسی و محتوای آموزشی مرتبط بررسی شود.

هدف:
- جلوگیری از طراحی بر اساس حدس
- شناسایی فعالیت‌های مشابه در پایه‌های مختلف
- جلوگیری از جا افتادن Modeهای مهم
- جلوگیری از ساخت Modeهای غیرضروری
- تطبیق سختی و تعامل با سن و هدف آموزشی

برای Spatial، بررسی نمونه‌های کتاب‌های درسی باید به‌صورت ویژه انجام شود؛ به‌خصوص فعالیت‌های مربوط به شکل و فضا، تقارن، دوران، انتقال، شبکه، تجسم و اجسام سه‌بعدی.

هر مورد استخراج‌شده از کتاب باید ابتدا به یکی از این دسته‌ها نسبت داده شود:
- Match / Place
- Find
- Arrange / Build
- Grid
- Direction / Path
- Symmetry
- Transform
- Hidden / Embedded Shapes
- 3D
- View / Projection
- Rotation in 3D
- Composite Spatial

اگر هیچ دسته‌ای مناسب نبود، قبل از ساخت Type جدید باید بررسی شود که آیا یکی از دسته‌های موجود قابل توسعه است.

==================================================
13. قانون ثبت در Git
==================================================

آخرین Commit پروژه معیار تشخیص وضعیت واقعی توسعه است.

در شروع هر مرحله جدید:
- Git status بررسی شود.
- آخرین Commit بررسی شود.
- وضعیت این سند با کد واقعی تطبیق داده شود.
- مرحله‌های انجام‌شده دوباره ساخته نشوند.
- قابلیت‌های فراموش‌شده یا نیمه‌کاره شناسایی شوند.

Rollback / Restore / تغییر معماری بدون تصمیم مستقیم کاربر انجام نشود.

هر تغییر:
یک هدف مشخص → تست → Commit → ثبت وضعیت
