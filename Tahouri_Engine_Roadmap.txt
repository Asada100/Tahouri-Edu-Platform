سند مرجع مسیر توسعه موتورهای طهوری
Tahouri Engine Development Roadmap
نسخه 1.0

وضعیت:
این سند مرجع اصلی ترتیب توسعه موتورهای آموزشی پروژه است.
در هر گفت‌وگوی جدید، مرحله توسعه باید با آخرین Commit پروژه تطبیق داده شود.
هدف سند این است که هنگام ساخت Activity جدید، تا حد امکان از موتور و قابلیت موجود استفاده شود و ساخت موتور جدید به حداقل برسد.

==================================================
1. اصل اصلی توسعه
==================================================

ترتیب تصمیم‌گیری برای هر قابلیت جدید:

ایده فعالیت
↓
بررسی موتورهای موجود
↓
بررسی Type / Mode / قابلیت موجود
↓
اگر لازم بود توسعه همان موتور
↓
اگر لازم بود Type / Mode جدید
↓
فقط در صورت ناتوانی واقعی معماری موجود، موتور جدید

در زمان ساخت بازی، ایده‌های جدید نباید به‌صورت خودکار باعث ساخت Engine جدید شوند.

یک قابلیت جدید ابتدا باید به‌عنوان «محتوا»، سپس «Type/Mode»، سپس «توسعه موتور موجود» بررسی شود.

==================================================
2. محدوده پروژه
==================================================

محدوده فعلی: پایه‌های اول تا ششم ابتدایی.
پیش‌دبستانی: پروژه آینده و فعلاً خارج از توسعه جاری.
متوسطه و دانشگاه: خارج از محدوده پروژه فعلی.

==================================================
3. موتورهای اصلی و ظرفیت آن‌ها
==================================================

1) Quiz Engine
وضعیت: فعال و آماده

کاربرد:
- سؤال چهارگزینه‌ای
- درست/غلط
- انتخاب تصویر
- انتخاب پاسخ
- سؤال همراه تصویر
- سؤال همراه صوت در صورت آماده بودن لایه صوت
- سنجش دانش و مفاهیم

اولویت: پایین؛ فقط تکمیل Typeهای موردنیاز.
قاعده: هر فعالیت سؤال‌محور ابتدا با Quiz بررسی شود.

--------------------------------------------------
2) Memory Engine
وضعیت: فعال و آماده

کاربرد:
- تصویر ↔ تصویر
- تصویر ↔ کلمه
- تصویر ↔ صوت
- عدد ↔ مقدار
- سؤال ↔ پاسخ
- حافظه توالی
- حافظه موقعیت

اولویت: متوسط.
قاعده: فعالیت‌هایی با هدف اصلی «به خاطر سپردن و بازیابی» ابتدا با Memory بررسی شوند.

--------------------------------------------------
3) Matching Engine
وضعیت: فعال و آماده

کاربرد:
- یک به یک
- چند مورد به یک مورد
- ارتباط مفهومی
- هم‌معنی
- متضاد
- تصویر ↔ کلمه
- صدا ↔ تصویر
- عدد ↔ مقدار
- شکل ↔ نام
- شیء ↔ کاربرد
- حیوان ↔ زیستگاه
- علت ↔ معلول
- سایر روابط دوطرفه

اولویت: خیلی بالا.
قاعده: برای روابط و تطبیق‌ها ابتدا Matching بررسی شود؛ موتور جدید ساخته نشود.

--------------------------------------------------
4) Classification Engine
وضعیت: فعال؛ نیازمند تکمیل ظرفیت

کاربرد:
- دسته‌بندی
- گروه‌بندی
- طبقه‌بندی تصویری
- طبقه‌بندی بر اساس ویژگی
- چند ویژگی
- انتخابی
- Drag & Drop
- Sorting در صورت پیاده‌سازی به‌عنوان Type/Mode
- فعالیت‌های چندمرحله‌ای

مورد مهم:
multiStageClassification باید به‌عنوان قابلیت رسمی موتور تکمیل و تست شود و دیگر فراموش نشود.

اولویت: بسیار بالا.

قاعده: Sorting تا حد امکان موتور مستقل نباشد و ابتدا به‌عنوان قابلیت Classification یا Puzzle بررسی شود.

--------------------------------------------------
5) Puzzle Engine
وضعیت: فعال و دارای ظرفیت بالا

ظرفیت‌ها:
- Sequence
- Ordering
- Sentence
- Grid
- Cross Grid
- Word Grid
- Input / Output
- Visual Math
- Jigsaw
- فعالیت‌های منطقی و مسئله‌محور

کاربردهای قابل توسعه:
- الگوها
- توالی‌ها
- ترتیب
- حل مسئله
- ادراک دیداری
- بعضی فعالیت‌های فضایی
- فعالیت‌های ریاضی تصویری

اولویت: بسیار بالا.

قاعده: قبل از ساخت Pattern یا Spatial Engine، ابتدا ظرفیت Puzzle و Typeهای آن بررسی شود.

توجه: Jigsaw فعلی تثبیت شده و بدون درخواست مستقیم نباید دستکاری شود.

--------------------------------------------------
6) Word Puzzle Engine
وضعیت: فعال و دارای ظرفیت توسعه زیاد

کاربرد:
- ساخت کلمه
- اتصال حروف با حرکت موس/لمس
- جست‌وجوی کلمات
- کلمات هم‌خانواده
- مرتب‌سازی حروف
- به‌هم‌ریختگی کلمات
- مسیرهای افقی و عمودی
- مسیرهای مورب
- حرکت L
- جدول حروف
- تصویر → کلمه
- صوت → کلمه در صورت آماده بودن لایه صوت

اولویت: بسیار بالا.
قاعده: برای فعالیت‌های واژگانی و ساخت کلمه ابتدا Word Puzzle بررسی شود.

--------------------------------------------------
7) Dictation Engine
وضعیت: فعال و تخصصی

کاربرد:
- املا
- جای‌گذاری حرف
- تشخیص نوشتار درست
- تمرین واژه
- جمله‌های املایی
- راهنمای حرف

اولویت: متوسط.
قاعده: Dictation نباید به موتور عمومی شنیداری تبدیل شود.

==================================================
4. قابلیت‌های رزروشده / نیازمند تکمیل
==================================================

A) multiStageClassification
اولویت: بسیار بالا
وضعیت: تکمیل و تست شود.

B) Pattern
اولویت: بالا
روش: ابتدا به‌صورت Type در Puzzle بررسی شود.
ساخت Engine مستقل ممنوع مگر اینکه ناتوانی Puzzle اثبات شود.

C) Spatial
اولویت: بالا
روش: ابتدا Puzzle / Matching / Jigsaw بررسی شود.
در صورت نیاز، Spatial Type ساخته شود.
Engine مستقل فعلاً ممنوع.

D) Auditory
اولویت: متوسط رو به بالا
پوشش فعلی محدود است.
ابتدا یک لایه/قابلیت صوتی مشترک بررسی شود؛ نه اینکه برای هر فعالیت موتور جدا ساخته شود.

E) Simulation
اولویت: آینده
وضعیت: رزرو.
فقط برای فعالیت‌هایی که واقعاً به شبیه‌سازی تعاملی نیاز دارند.

F) Story
اولویت: آینده
وضعیت: رزرو.
فعالیت‌های ساده داستانی ابتدا با Puzzle / Quiz بررسی شوند.

6. ترتیب اولویت توسعه
==================================================

مرحله 1 — تثبیت و تکمیل موتورهای موجود
- بررسی همه Engineهای فعال
- ثبت Type/Modeهای موجود
- رفع قابلیت‌های نیمه‌کاره
- تکمیل multiStageClassification
- اطمینان از عدم شکست موتورهای قبلی

مرحله 2 — توسعه ظرفیت موتورهای پرکاربرد
- Matching
- Classification
- Puzzle
- Word Puzzle
- Memory
- Quiz

این مرحله باید موازی پیش برود و لازم نیست هر موتور کاملاً جداگانه تمام شود.

مرحله 3 — تکمیل قابلیت‌های عمومی
- Pattern به‌عنوان Puzzle Type
- Spatial به‌عنوان Puzzle/Type
- Sorting در Classification/Puzzle
- Typeهای عمومی Word Puzzle
- Typeهای عمومی Matching

مرحله 4 — زیرساخت‌های مشترک
- Audio Layer
- Interactionهای مشترک
- Touch/Mouse
- Hint
- Feedback
- Accessibility
- ابزارهای مشترک UI

مرحله 5 — موتورهای واقعاً جدید
فقط پس از اثبات اینکه موتورهای موجود و Typeهای آن‌ها قادر به اجرای نیاز نیستند:
- Auditory مستقل
- Simulation
- Story
- یا هر Engine جدید دیگر

==================================================
7. روش کار موازی
==================================================

توسعه نباید الزاماً به شکل «یک موتور کامل شود → موتور بعدی» باشد.

چند Track می‌توانند هم‌زمان جلو بروند:

Track A: Classification و multiStageClassification
Track B: Typeهای Puzzle
Track C: Matching
Track D: Word Puzzle
Track E: Memory / Quiz / Dictation در صورت نیاز
Track F: زیرساخت‌های مشترک

هر Track باید هدف مشخص، تست و Commit مستقل داشته باشد.

==================================================
8. قانون جلوگیری از فراموشی
==================================================

هیچ قابلیت شناخته‌شده‌ای نباید به دلیل درگیری با خطای دیگری فراموش شود.

هر قابلیت نیمه‌کاره باید یکی از این وضعیت‌ها را داشته باشد:

[ACTIVE] در حال توسعه
[READY] آماده استفاده
[TESTING] در حال تست
[BLOCKED] به دلیل مشخص متوقف
[RESERVED] برای مرحله آینده
[DEPRECATED] دیگر مورد استفاده نیست

multiStageClassification باید همیشه وضعیت مشخص داشته باشد.

==================================================
9. قانون شروع هر Activity جدید
==================================================

1. هدف آموزشی مشخص شود.
2. موتور مناسب انتخاب شود.
3. Type/Mode موجود بررسی شود.
4. اگر وجود دارد، همان استفاده شود.
5. اگر ناقص است، همان Type توسعه داده شود.
6. اگر وجود ندارد، Type جدید بررسی شود.
7. فقط اگر هیچ موتور موجود مناسب نبود، پیشنهاد Engine جدید مطرح شود.

ایده جدید مساوی موتور جدید نیست.

==================================================
10. قانون تصمیم‌گیری درباره Engine جدید
==================================================

ساخت Engine جدید فقط وقتی مجاز است که:
- چند Activity واقعی به آن نیاز داشته باشند؛
- موتورهای موجود نتوانند نیاز را پوشش دهند؛
- ساخت Type جدید در موتور موجود کافی نباشد؛
- افزودن قابلیت به موتور موجود باعث خراب شدن مسئولیت آن موتور نشود؛
- معماری فعلی حفظ شود.

==================================================
11. وضعیت ثبت در Git
==================================================

آخرین Commit پروژه معیار تشخیص وضعیت واقعی توسعه است.

در شروع هر مرحله جدید:
- Git status بررسی شود.
- آخرین Commit بررسی شود.
- وضعیت این سند با کد واقعی تطبیق داده شود.
- مرحله‌های انجام‌شده دوباره ساخته نشوند.
- قابلیت‌های فراموش‌شده یا نیمه‌کاره شناسایی شوند.

Rollback / Restore / تغییر معماری بدون تصمیم مستقیم کاربر انجام نشود.

هر تغییر:
یک هدف مشخص → تست → Commit → ثبت وضعیت

==================================================
12. قاعده نهایی پروژه
==================================================

ابتدا ظرفیت موجود را کامل استفاده می‌کنیم،
سپس آن را توسعه می‌دهیم،
بعد Type جدید می‌سازیم،
و فقط در صورت نیاز واقعی Engine جدید می‌سازیم.

هدف:
کمترین تعداد Engine
+ بیشترین قابلیت
+ معماری پایدار
+ توسعه موازی
+ عدم فراموشی قابلیت‌های نیمه‌کاره
+ جلوگیری از پراکنده شدن پروژه به دلیل ایده‌های لحظه‌ای
