# قرارداد داده صفحه مختصات عددی — نسخه 1.0

وضعیت: DESIGN / پیش از پیاده‌سازی  
دامنه: توسعه محدود Spatial موجود؛ بدون Engine جدید و بدون تغییر معماری Puzzle  
مخزن: `Asada100/Tahouri-Edu-Platform`

## 1. هدف

تعریف قرارداد داده برای صفحه مختصات دکارتی واقعی. صفحه مختصات با Grid خانه‌ای `place` یا تقارن محوری موجود یکی فرض نمی‌شود. این سند به‌تنهایی به معنی پیاده‌سازی قابلیت نیست.

## 2. قرارداد پایه Activity

نمونه پیشنهادی:

```json
{
  "type": "spatial",
  "mode": "coordinatePlane",
  "coordinateSystem": {
    "xMin": -4,
    "xMax": 4,
    "yMin": -3,
    "yMax": 3,
    "unitStep": 1,
    "showAxes": true,
    "showGrid": true
  },
  "task": {
    "kind": "placePoint",
    "target": { "x": -2, "y": 3 }
  }
}
```

- `x` و `y` عددهای ریاضی‌اند، نه شماره ردیف و ستون HTML.
- محور (x) از چپ به راست افزایش می‌یابد؛ محور (y) در دستگاه ریاضی از پایین به بالا افزایش می‌یابد.
- تبدیل به مختصات صفحه‌نمایش فقط در لایه نمایش انجام می‌شود؛ کوچک یا بزرگ‌شدن صفحه نباید پاسخ ریاضی را تغییر دهد.
- مقدارهای `xMin`، `xMax`، `yMin`، `yMax` باید عدد متناهی باشند و حداقل هر دو بازه طول مثبت داشته باشند.
- `unitStep` باید مثبت باشد و محدوده‌ها باید با گام انتخاب‌شده سازگار باشند.
- مختصات خارج از محدوده رد می‌شود؛ نباید بی‌صدا به نزدیک‌ترین نقطه تبدیل شود.

## 3. انواع تمرین مجاز در گام اول

1. `readPoint`: نمایش نقطه و دریافت مختصات `{x, y}`.
2. `placePoint`: دریافت مختصات هدف و درخواست قرار دادن نقطه روی صفحه.
3. `identifyPoint`: نمایش چند نقطه نام‌گذاری‌شده و پرسش درباره مختصات یک نقطه.

گام اول فقط یک نقطه و یک پاسخ را پشتیبانی کند. چندنقطه‌ای، مختصات اعشاری، تبدیل واحد، دوران و تقارن نقطه‌ای خارج از این نسخه‌اند مگر آنکه بعداً جداگانه طراحی شوند.

## 4. اعتبارسنجی

پیش از شروع فعالیت، داده باید رد شود اگر:
- محدوده یا گام ناموجود، غیرعددی، نامتناهی یا نامعتبر باشد؛
- مختصات هدف ساختار معتبر `x` و `y` نداشته باشد؛
- مختصات هدف خارج از محدوده باشد؛
- نوع تمرین ناشناخته باشد؛
- فهرست نقاط برای `identifyPoint` خالی باشد یا شناسه‌های تکراری داشته باشد.

در داده نامعتبر، فعالیت نباید با هدف جایگزین یا نقطه جابه‌جا شده اجرا شود.

## 5. قرارداد تبدیل مختصات

برای بازه دیداری صفحه `left..right` و `top..bottom`:
- مقدار (x) با افزایش از چپ به راست نگاشت می‌شود.
- مقدار (y) با افزایش از پایین به بالا نگاشت می‌شود؛ بنابراین در مختصات CSS مقدار y دیداری وارونه است.
- تبدیل رفت‌وبرگشت باید با خطای حداکثر نصف فاصله گام، برای مختصات شبکه‌ای، همان نقطه را بازیابی کند.
- hit-testing باید بر اساس نزدیک‌ترین نقطه شبکه‌ای و آستانه لمس مشخص انجام شود؛ اگر لمس بیرون از آستانه یا محدوده باشد، پاسخ ثبت نشود.

## 6. آزمون‌های پذیرش پیش از READY

- چهار ربع و نقاط روی هر دو محور درست نمایش داده شوند.
- مختصات منفی، صفر و مثبت به مکان درست نگاشت شوند.
- تغییر اندازه ظرف، جهت دستگاه و اندازه صفحه مختصات ریاضی را تغییر ندهد.
- تبدیل ریاضی به پیکسل و برگشت، مختصات شبکه‌ای را حفظ کند.
- محدوده و گام نامعتبر و هدف خارج از محدوده رد شوند.
- لمس بیرون از صفحه یا خارج از آستانه پاسخ را ثبت نکند.
- قراردادهای فعلی `legacy`, `place`, `symmetry` بدون تغییر رفتار باقی بمانند.

## 7. ترتیب کار

1. تطبیق نوع تمرین با محتوای واقعی کتاب پایه ششم و انتخاب یک نمونه آموزشی کوچک.
2. پیاده‌سازی validator و تست داده‌ها، مستقل از UI.
3. پیاده‌سازی نگاشت مختصات و آزمون‌های تبدیل.
4. اتصال محدود به Spatial موجود و UI.
5. اجرای regression کامل؛ سپس آزمایش عملی مرورگر/موبایل.
6. بررسی تقارن نقطه‌ای فقط پس از تثبیت قرارداد مختصات.

## 8. محدودیت

این فایل فقط قرارداد طراحی است؛ تا زمانی که handler، UI و آزمون‌های مرتبط اضافه و اجرا نشده‌اند، `coordinatePlane` نباید قابلیت آماده یا پیاده‌سازی‌شده اعلام شود.
