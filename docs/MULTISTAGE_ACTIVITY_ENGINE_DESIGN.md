# طراحی موتور فعالیت چندمرحله‌ای ترکیبی

**وضعیت:** سند طراحی و ممیزی؛ هنوز تغییری در رفتار اجرایی موتور اعمال نشده است.  
**مبنای بررسی:** شاخهٔ `master`، پس از ثبت فعالیت آزمایشی `multiStageAnimalJourney` در ۹ اکتبر ۲۰۲۶.

## ۱. تصمیم معماری

هدف این قابلیت فقط «چند مرحله از یک نوع بازی» نیست. هدف، یک فعالیت آموزشی واحد است که در آن هر مرحله می‌تواند رابطه یا تعامل متفاوتی آموزش دهد؛ برای نمونه:

- تصویر ← انتخاب واژه
- صوت ← انتخاب تصویر
- واژه یا جمله ← انتخاب تصویر
- اتصال متن به صوت
- دسته‌بندی یا تطبیق در مرحلهٔ پایانی

برای این هدف، `multiStage` نباید برای همیشه زیرمجموعهٔ منطق دسته‌بندی باقی بماند. با این حال، نباید همهٔ موتورهای موجود را یک‌باره بازنویسی کرد یا منطق آن‌ها را کپی کرد.

**تصمیم پیشنهادی:** ایجاد یک هماهنگ‌کنندهٔ سبک برای فعالیت مرکب، با قرارداد روشن برای مرحله‌ها و آداپتورهای محدود؛ موتورهای موجود تا حد امکان حفظ شوند. پیاده‌سازی باید مرحله‌ای باشد و هر مرحله با آزمون مستقل تأیید شود.

## ۲. وضعیت فعلی تأییدشده

### موتور دسته‌بندی چندمرحله‌ای

- فایل اصلی: `engine/activity/classificationEngine.js`
- تأمین محتوا: `engine/question/classificationProvider.js`
- نوع چندمرحله‌ای: `engine/activity/classificationTypes/multiStageClassification.js`
- رابط: `engine/ui/classificationScreen.js`

در وضعیت فعلی، `ClassificationProvider` فقط دو حالت مرحله را می‌پذیرد: `choice` و `dragDrop`. رابط دسته‌بندی، آیتم‌های `type: "image"` را نمایش می‌دهد، اما صوت را به‌عنوان نوع محتوا پشتیبانی نمی‌کند. نوع چندمرحله‌ای فعلی فقط صحت دسته‌بندی را ارزیابی می‌کند؛ موتور دیگری را در هر مرحله اجرا نمی‌کند.

### قابلیت‌های موجود که باید دوباره استفاده شوند

- موتور تطبیق: `engine/activity/matchingEngine.js`
- رابط تطبیق: `engine/ui/matchingScreen.js`
- موتورهای دیگر از طریق چرخهٔ عمومی فعالیت و رویدادهای `activityReady` و `activityFinished` متصل می‌شوند.

موتور تطبیق از نمایش تصویر در دو سوی تطبیق پشتیبانی می‌کند؛ اما پشتیبانی عمومی از صوت و هماهنگ‌سازی آن در یک فعالیت مرکب، از بررسی فعلی تأیید نمی‌شود.

## ۳. قرارداد پیشنهادی فعالیت مرکب

فعالیت مرکب یک فهرست مرتب از مرحله‌ها دارد. هر مرحله باید دست‌کم شامل این مفاهیم باشد:

- `id`: شناسهٔ یکتای مرحله
- `title` و `instruction`: عنوان و راهنمای همان مرحله
- `interaction`: نوع تعامل، مانند `classification` یا `matching`
- `content`: داده‌های مخصوص همان تعامل
- `scoring`: سیاست امتیازدهی مرحله، در صورت نیاز
- `completion`: شرط پایان مرحله

نوع تعامل باید از نوع رسانه جدا باشد. برای نمونه، `image` و `audio` نوع محتوا هستند، اما `matching` و `choice` نوع تعامل‌اند. این دو مفهوم نباید در یک فیلد ادغام شوند.

نمونهٔ مفهومی (صرفاً برای توضیح قرارداد؛ هنوز قالب اجرایی نیست):

```json
{
  "mode": "composite",
  "stages": [
    {
      "id": "picture-to-word",
      "interaction": "choice",
      "content": {
        "prompt": { "type": "image", "src": "assets/animal.jpg" },
        "options": [
          { "id": "cat", "type": "text", "value": "گربه" },
          { "id": "fish", "type": "text", "value": "ماهی" }
        ],
        "answerId": "cat"
      }
    },
    {
      "id": "sound-to-picture",
      "interaction": "choice",
      "content": {
        "prompt": { "type": "audio", "src": "assets/animal-sound.mp3" },
        "options": [
          { "id": "bird", "type": "image", "src": "assets/bird.jpg" },
          { "id": "frog", "type": "image", "src": "assets/frog.jpg" }
        ],
        "answerId": "bird"
      }
    }
  ]
}
```

این نمونه قرارداد پیشنهادی است؛ نباید پیش از پیاده‌سازی و اعتبارسنجی، به‌عنوان محتوای قابل اجرا وارد `data/activities.json` شود.

## ۴. مسئولیت‌ها

### هماهنگ‌کنندهٔ مرکب

- آغاز فعالیت و مرحلهٔ اول
- نگهداری شاخص مرحله، پیشرفت کلی و نتیجهٔ نهایی
- جلوگیری از اجرای دوبارهٔ مرحله یا پایان فعالیت
- انتقال به مرحلهٔ بعد فقط پس از دریافت پایان موفق از مرحلهٔ جاری
- جمع‌کردن نتیجه‌ها و ارسال دقیقاً یک رویداد نهایی `activityFinished`
- پشتیبانی از بازگشت/بازیابی نشست، فقط پس از تعریف قرارداد سازگار

### آداپتور مرحله

هر آداپتور باید راه یکسانی برای شروع، دریافت نتیجه، پاک‌سازی و گزارش پایان فراهم کند؛ جزئیات داخلی موتورهای موجود نباید به هماهنگ‌کننده نشت کند. ابتدا فقط آداپتورهایی اضافه شوند که برای یک نمونهٔ واقعی لازم‌اند.

### نمایش محتوا

نمایش متن، تصویر و صوت باید از نوع تعامل جدا باشد. برای صوت باید کنترل قابل استفاده با ماوس، لمس و صفحه‌کلید، وضعیت بارگذاری/خطا، و عدم پخش خودکار ناخواسته در نظر گرفته شود.

## ۵. ترتیب پیاده‌سازی پیشنهادی

1. **جداگانه بررسی و رفع چرخهٔ پایان فعالیت فعلی.** در آزمایش `multiStageAnimalJourney`، پس از نمایش نتیجه اجرای مجدد مشاهده شده است. علت هنوز مشخص نشده و نباید با حدس تغییر داده شود.
2. نوشتن آزمون‌های قرارداد و چرخهٔ عمر هماهنگ‌کننده: شروع، پایان یک مرحله، انتقال، پایان کل، و جلوگیری از رویداد نهایی تکراری.
3. پیاده‌سازی حداقل هماهنگ‌کننده، بدون تغییر رفتار فعالیت‌های عادی.
4. افزودن یک نمونهٔ واقعی «تصویر ← واژه» با استفاده از قابلیت‌های موجود تا حد امکان.
5. افزودن مرحلهٔ «صوت ← تصویر» فقط پس از تأیید بارگذاری فایل، کنترل پخش و خطاها.
6. آزمون رگرسیون برای فعالیت‌های عادی دسته‌بندی و تطبیق، و آزمون نهایی در دسکتاپ و موبایل.

## ۶. معیارهای پذیرش

- فعالیت عادی فعلی بدون تغییر رفتار ادامه یابد.
- هر مرحله نوع تعامل و محتوای خودش را تعریف کند.
- پایان هر مرحله باعث اجرای فقط یک انتقال شود.
- پایان کل فعالیت فقط یک نتیجه و یک رویداد نهایی تولید کند.
- درصد و امتیاز نهایی از نتیجه‌های مرحله‌ها محاسبه شوند، نه از شمارندهٔ مرحلهٔ جاری.
- تصویر یا صوت خراب/در دسترس‌نبودنی باعث قفل‌شدن بی‌پایان فعالیت نشود.
- مسیر بازگشت و تکمیل فعالیت‌های فعلی همچنان کار کند.
- هیچ موتور تازه‌ای ساخته نشود اگر آداپتور کوچک روی موتور موجود کافی است.

## ۷. خارج از دامنهٔ مرحلهٔ اول

- بازنویسی همهٔ موتورهای بازی
- افزودن همهٔ انواع تعامل در یک تغییر
- تغییر معماری کلی `ActivityManager` یا `EngineManager`
- تغییر فعالیت آزمایشی فعلی به‌عنوان اثبات پشتیبانی از صوت

**گام بعدی اجرایی:** اول علت اجرای مجدد پس از پایان را جداگانه ردیابی و آزمون کنیم؛ سپس هماهنگ‌کننده را در یک تغییر مستقل اضافه کنیم.
