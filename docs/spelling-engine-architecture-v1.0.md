# سند جامع موتور املا — Tahouri Edu Platform
## نسخه 1.0 — 2026-09-27

## 1. هدف
این سند مرجع طراحی، معماری و توسعه موتور املا در Tahouri است. هدف، ساخت یک سیستم املا برای دانش‌آموزان ابتدایی است که از روش واقعی آموزشی پروژه پشتیبانی کند و در عین حال با Quiz، Memory، Puzzle، Matching و Classification ترکیب معماری پیدا نکند.

اصل کلیدی:
**یک موتور املا، چند حالت سؤال مستقل، داده جدا از منطق، و رسانه جدا از موتور.**

---

## 2. روش‌های آموزشی موردنیاز

### 2.1 تکمیل حروف حذف‌شده — Missing Letter
اصل واژه وجود دارد و یک یا چند حرف از آن حذف می‌شود.

نمونه:
- نـ....ـراسیم → نهراسیم
- مـ....ـبت → محبت
- مو....ون → موزون
- مَر....زار → مرغزار

نقطه‌چین صرفاً نشانه حذف است. پس از ورود صحیح، نقطه‌چین حذف و حرف واقعی در جای خودش نمایش داده می‌شود.

### 2.2 Guided Word
دانش‌آموز کلمه را از ابتدا می‌نویسد. کیبورد سه ردیف اصلی فارسی دارد:
- حروف موجود در واژه فعال هستند.
- سایر حروف خاموش هستند.
- فقط حرف بعدی به‌صورت راهنمای کم‌رنگ نمایش داده می‌شود.
- ورود حرف اشتباه متوقف می‌شود و پاسخ ثبت‌شده تغییر نمی‌کند.
- در پایان کلمه، تکمیل خودکار انجام می‌شود.

### 2.3 Context / Sentence Cloze
کلمه در جمله یا متن درس قرار دارد و بخشی از آن حذف می‌شود. با تکمیل یک کلمه، همان کلمه تأیید می‌شود و تمرکز به هدف بعدی می‌رود.

### 2.4 Context + Image
تصویر فقط یک رسانه کمکی است و هرگز بخشی از منطق موتور املا نیست. وجود تصویر اختیاری است.

## 3. اصل آموزشی املای Tahouri
پاسخ صحیح فقط از روی رشته حروف تعیین نمی‌شود. سؤال باید بتواند به:
- متن درس
- جمله
- واژه هدف
- قاعده املایی
- گروه حروف هم‌آوا/چندشکل
متصل باشد.

مثال:
صدای «س» می‌تواند هدف آموزشی گروه «س/ص/ث» باشد.
صدای «ز» می‌تواند گروه «ز/ذ/ض/ظ» باشد.
این گروه‌ها در داده آموزشی ثبت می‌شوند؛ موتور نباید خودش پاسخ ادبی یا املایی را حدس بزند.

**مرجع نهایی پاسخ، محتوای تأییدشده درس است.**

## 4. معماری مصوب

### 4.1 مرزهای اصلی
```
Content
  ↓
Spelling Question Generator
  ↓
DictationProvider
  ↓
DictationEngine
  ↓
DictationScreen
```

رسانه:
```
Question
 ├─ text/context
 ├─ target
 └─ media (optional)
      ├─ image
      ├─ audio
      └─ future media
```

### 4.2 مسئولیت‌ها

#### DictationEngine
مسئول:
- state
- current question
- input validation
- progress
- scoring
- completion
- events

نباید مسئول:
- تولید سؤال
- تشخیص خودکار پاسخ از متن
- تولید تصویر
- مدیریت فونت
- ساخت محتوای درس

#### DictationProvider
مسئول:
- خواندن و نرمال‌سازی داده املا
- تبدیل داده خام به مدل استاندارد سؤال
- حفظ backward compatibility با داده‌های قدیمی

#### SpellingQuestionGenerator
مسئول:
- انتخاب واژه از محتوای تأییدشده
- انتخاب حرف/حروف هدف
- ساخت missing-letter
- اتصال به جمله/متن
- اتصال به spellingRule
- انتخاب سطح دشواری

#### DictationScreen
مسئول:
- نمایش سؤال
- نمایش کلمه و جای حذف
- نمایش کیبورد
- نمایش راهنمای حرف بعدی
- دریافت کلیک/کیبورد فیزیکی
- نمایش بازخورد

### 4.3 اصل مهم
**هیچ تغییر معماری در EngineManager یا زنجیره Activity لازم نیست.**
موتور همچنان با:
ActivityManager → EngineManager → DictationEngine → DictationScreen
کار می‌کند.

## 5. مدل داده پیشنهادی

نمونه Missing Letter:

```json
{
  "id": "lesson1-spelling-01",
  "mode": "missing-letter",
  "prompt": "املای کلمات را با توجه به متن درس کامل کنید.",
  "context": "پسر دلبندم...",
  "answer": "نهراسیم",
  "masked": "نـــ....راسیم",
  "missing": [
    {
      "start": 1,
      "length": 1,
      "answer": "ه"
    }
  ],
  "spellingRule": "ه",
  "lesson": "lesson1",
  "media": null
}
```

برای گروه املایی:

```
"spellingRule": {
  "id": "s-sad-se",
  "sound": "س",
  "letters": ["س", "ص", "ث"]
}
```

## 6. نقطه‌چین و نمایش

برای نسخه فعلی:
- نقطه‌چین حفظ می‌شود.
- رنگ آن از متن اصلی متمایز اما ملایم است.
- نقطه‌چین بخشی از پاسخ نیست.
- بعد از ورود صحیح، جای آن با حروف واقعی جایگزین می‌شود.
- برای چند حرف، نقطه‌چین می‌تواند یک بخش پیوسته باشد.
- استفاده از bracket، مربع و کادر برای جای خالی ممنوع است.

نمایش باید با فونت واقعی محتوای فارسی پروژه انجام شود. موتور نباید به فونت خاصی وابسته شود؛ CSS/asset layer مسئول فونت است.

---

## 7. اتصال حروف فارسی
در Missing Letter، حرف واردشده باید در همان موقعیت واقعی واژه قرار بگیرد تا شکل اتصال فارسی طبیعی باشد.

مثلاً هدف «ه» در:
نهراسیم

نباید به‌صورت یک دکمه یا متن جداگانه کنار کلمه نمایش داده شود؛ باید داخل جریان تایپوگرافی واژه قرار بگیرد.

---

## 8. کیبورد Guided Word

سه ردیف اصلی حروف فارسی نمایش داده می‌شود.

حالت‌های کلید:
- active: حرف در واژه وجود دارد.
- disabled: حرف در واژه وجود ندارد.
- expected: حرف مورد انتظار فعلی.
- feedback-correct: بازخورد کوتاه پس از ورود صحیح.
- feedback-wrong: بازخورد کوتاه بدون ثبت حرف غلط.

کلید Space در صورت نیاز در بخش کنترل‌های طبیعی کیبورد قرار می‌گیرد و «دکمه ویژه فاصله» یا «نیم‌فاصله» ساخته نمی‌شود.

کیبورد باید از input native استفاده نکند تا پیشنهادهای سیستم‌عامل/مرورگر وارد تجربه آموزشی نشود.

---

## 9. رفتار Guided Word

برای «مدرسه»:

حالت شروع:
```
[م]  به‌صورت راهنمای کم‌رنگ
```

ورود «م»:
```
م [د]
```

ورود اشتباه «ر»:
```
م [د]
```
و حرف ر ثبت نمی‌شود.

ورود «د»:
```
مد [ر]
```

در هر لحظه فقط یک حرف آینده به‌عنوان راهنما دیده می‌شود.

## 10. حالت Missing Letter

دانش‌آموز فقط بخش حذف‌شده را تکمیل می‌کند.

در صورت چند جای خالی، ترتیب فعال‌شدن آن‌ها باید در داده سؤال مشخص باشد.

اشتباه:
- حرف اشتباه ثبت نمی‌شود.
- جای خالی باقی می‌ماند.
- بازخورد کوتاه داده می‌شود.

صحیح:
- حرف وارد می‌شود.
- نقطه‌چین همان بخش جایگزین می‌شود.
- اگر همه بخش‌های هدف کامل شده‌اند، واژه صحیح تأیید می‌شود.
- سپس سؤال بعدی فعال می‌شود.

## 11. سطح‌بندی

Level 1:
- یک حرف حذف‌شده
- واژه آشنا
- بدون تصویر

Level 2:
- یک یا چند حرف
- واژه‌هایی با حروف چندشکل

Level 3:
- واژه در جمله/متن
- حروف هدف از گروه‌های املایی

Level 4:
- جمله + تصویر اختیاری
- چند هدف در یک متن
- انتخاب دشواری بر اساس عملکرد قبلی

## 12. سؤال‌ساز هوشمند

Question Generator نباید با AI پاسخ نهایی را حدس بزند.

ورودی:
- متن درس تأییدشده
- فهرست واژه‌های هدف
- قواعد املایی
- سطح پایه
- سطح دشواری

خروجی:
- سؤال معتبر
- پاسخ قطعی
- جای حذف
- قاعده هدف
- منبع درس

AI در آینده فقط می‌تواند پیشنهاددهنده باشد؛ تأیید نهایی با محتوای آموزشی است.

---

## 13. گروه‌های املایی
قواعد باید داده‌محور باشند، نه hard-code داخل UI.

نمونه:
- س/ص/ث
- ز/ذ/ض/ظ
- ت/ط
- ه/ح
- ق/غ

این فهرست باید قابل توسعه باشد و برای هر واژه فقط در صورتی استفاده شود که آن قاعده واقعاً در متن آموزشی موردنظر تدریس شده باشد.

---

## 14. تصاویر

### اصل
برای هر واژه یک تصویر اختصاصی تولید نمی‌کنیم.

### راهبرد
1. کتابخانه تصاویر مفهومی کم‌حجم
2. تصاویر ترکیبی از عناصر پایه
3. تصاویر اختصاصی فقط برای مفاهیم ضروری

تصویر باید:
- نقش آموزشی داشته باشد
- پاسخ را بدون فکر کردن لو ندهد
- حجم کنترل‌شده داشته باشد
- سبک بصری ثابت داشته باشد

### قالب پیشنهادی
برای تصاویر ساده:
- SVG در صورت امکان
- WebP برای تصاویر raster
- اندازه متناسب با نمایش، نه فایل دوربین/عکس بزرگ

### معماری رسانه
تصویر یک dependency اختیاری سؤال است؛ DictationEngine نباید منطق تصویر داشته باشد.

## 15. فونت
فونت بخشی از Presentation/Assets است، نه Engine.

در حال حاضر موتور املا نباید هیچ مسیر hard-code برای MJ Faraz داشته باشد. اگر فونت در assets پروژه موجود باشد، CSS آن را بارگذاری می‌کند.

وجود/عدم وجود فونت باید در مرحله asset audit بررسی شود و حذف ناخواسته فایل‌های قبلی بدون بررسی Git انجام نشود.

## 16. امتیازدهی
در Missing Letter:
- تکمیل صحیح سؤال = پاسخ صحیح
- خطای حرفی می‌تواند به‌صورت جداگانه برای تحلیل ثبت شود.
- خطای حرف نباید لزوماً یک «پاسخ غلط کامل» محسوب شود.

داده عملکرد:
```
question
target
rule
typed
characterErrors
completed
time
```

این امکان را می‌دهد بفهمیم دانش‌آموز مثلاً در «س/ص/ث» مشکل دارد، بدون اینکه کل سؤال را غلط اعلام کنیم.

## 21. تصمیم معماری نهایی

**یک DictationEngine اصلی حفظ می‌شود.**

درون آن فقط یک قرارداد مشترک برای حالت‌های املا وجود دارد. حالت‌های سؤال نباید به صورت Engineهای مستقل ثبت شوند.

```
EngineManager
   └── dictation
         └── DictationEngine
               ├── missing-letter
               ├── guided-word
               └── context
```

این تصمیم عمداً از ایجاد چند Engine موازی جلوگیری می‌کند و در عین حال اجازه می‌دهد رفتار هر حالت مستقل و قابل تست باقی بماند.

## 23. معیار موفقیت
موتور زمانی آماده انتشار داخلی است که:
1. هر سه حالت اصلی بدون تغییر EngineManager کار کنند.
2. نمونه‌های واقعی معلم قابل ورود به JSON باشند.
3. سؤال‌ها بدون تصویر هم کامل باشند.
4. تصویر فقط در صورت وجود نمایش داده شود.
5. خطای یک حرف با خطای کل سؤال قاطی نشود.
6. ظاهر فارسی با فونت پروژه طبیعی باشد.
7. هیچ Engine دیگر تحت تأثیر قرار نگیرد.
8. اضافه‌کردن یک روش جدید املا نیازمند ساخت Engine جدید نباشد.

این سند مرجع توسعه موتور املا در Tahouri است.
