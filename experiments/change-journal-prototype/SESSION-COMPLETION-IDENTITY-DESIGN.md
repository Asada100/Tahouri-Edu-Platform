# Session and Completion Identity — Design Proposal

**Status:** proposal only; not runtime implementation  
**Branch:** `experiment/local-change-journal-prototype`  
**Date:** 2026-11-27  
**Decision required before implementation:** yes

## 1. Problem being solved

The current `ActivitySessionManager.begin()` creates IDs using:

```js
"activity-session-" + activity.id + "-" + Date.now()
```

The browser diagnostic reproduced two defects:

- Two fresh attempts created during the same millisecond can receive the same ID.
- The same activity started for two profiles at the same timestamp can receive the same ID.

The ID is persisted and retained on resume, which is useful, but its generation is not collision-resistant. A timestamp is metadata, not a unique identity.

## 2. Proposed identity format

Use a cryptographically secure random UUID v4 as the attempt/session identity.

Preferred API:

```js
crypto.randomUUID()
```

Compatibility fallback, only when `randomUUID` is unavailable:

1. Require `crypto.getRandomValues`.
2. Generate 16 random bytes using that cryptographic API.
3. Set the RFC 4122 version-4 and variant bits.
4. Format the bytes as a UUID v4 string.
5. Never fall back to `Math.random()`, timestamps, activity IDs, profile IDs, or counters as entropy.

If neither cryptographic API is available, identity generation must fail closed. Do not silently create a timestamp-based ID and mark it as safe for journal publication.

### Verified caller behavior and no-crypto decision

A source trace on this branch verified that `ActivityManager.start()` calls `ActivitySessionManager.begin()` before engine startup and aborts the activity start if `begin()` returns a falsy value. Therefore, a fail-closed generator with no alternate path would prevent the student from starting the activity in an environment without a cryptographic random source.

This is a product/runtime decision, not something to hide inside the UUID helper. Before implementation, choose and test one explicit policy:

- **Strict policy:** do not start an activity if a secure session identity cannot be generated or persisted. Show a clear recoverable error rather than silently failing.
- **Degraded local-only policy:** allow the activity to run without a resumable session, but mark it explicitly non-resumable and non-journal-eligible; verify every lifecycle and completion path handles the absence safely. Never mint a timestamp ID as if it were secure.

Do not choose the degraded policy until all consumers of `currentSession` and all `begin()` callers are traced. The current caller in `ActivityManager.start()` aborts when `begin()` returns null, so degraded behavior would require a deliberate, separately tested caller change.

Suggested shape:

```js
{
  id: "activity-session-<uuid-v4>",
  identityVersion: 2,
  profileId: "<validated active profile>",
  activityId: "<catalog activity id>",
  startedAt: 0,
  updatedAt: 0,
  // existing session fields remain unchanged
}
```

The UUID is globally collision-resistant across profiles and activity IDs. The profile ID remains an authorization/namespace attribute; it is not part of the uniqueness mechanism.

## 3. Session and completion identity relationship

One persisted activity session represents one attempt. For a single-attempt activity completion, derive the stable completion key from the persisted session identity:

```js
completionId = "completion:" + session.id
```

This value is not regenerated by an event consumer. All completion publishers and the central lifecycle fan-out must use the same persisted session identity. Duplicate delivery of the same attempt therefore carries the same completion ID.

Do not use `activityId`, question index, timestamp, or profile ID alone as a completion ID. Do not generate a new completion ID each time a terminal event is delivered.

If product semantics later allow multiple separately recorded completions inside one session, that is a different identity model and requires a new explicit design; it must not be inferred in this implementation.

## 4. Lifecycle rules

### New attempt

- Generate one UUID before persisting the session and before engine startup.
- Persist the session successfully before treating the attempt as resumable or journal-eligible.
- A new attempt after explicit restart or completion receives a new UUID, even when the activity and clock timestamp are unchanged.
- The existing guard that prevents duplicate `begin()` calls for the same active attempt must continue returning the existing session rather than minting another ID.

### Resume

- A valid resumable session keeps exactly the same ID.
- Reload, restore, and `capture()` must never rotate the ID.
- The resumed engine must publish completion using the original attempt identity.
- If migration or persistence of the identity cannot be completed safely, do not publish a journal-eligible completion.

### Profile change

- Each session must contain the validated active `profileId`.
- A session from another profile must not be loaded or resumed.
- UUID uniqueness is global; profile-scoped storage remains an independent isolation layer.
- Tests must use the same activity and fixed clock for two synthetic profiles and assert distinct IDs and separate storage keys.

### Missing or invalid identity

- A completion consumer must never invent an identity.
- If no valid persisted session identity is available at completion time, mark the completion as not journal-eligible and emit an explicit diagnostic. Existing learning behavior must not be silently counted as safely synchronized.
- The precise user-facing behavior and whether gameplay continues without resumable persistence must be decided after tracing every caller of `begin()`; this proposal does not authorize changing that behavior.

## 5. Legacy session compatibility

Existing sessions use schema version 1 and timestamp-derived IDs. They may be needed to resume an in-progress activity, so do not delete them or blindly reject them.

Proposed one-time migration:

1. Validate the legacy session using the existing profile, activity, status, and engine-state checks.
2. Preserve the old ID in `legacyId` for diagnostics and recovery.
3. Generate a cryptographically secure UUID v4 for the new `id`.
4. Set `identityVersion: 2` and increment the session schema version.
5. Persist the migrated snapshot successfully before restoring the engine.
6. Resume using the new ID and keep it stable thereafter.
7. If secure randomness or persistence fails, retain the original stored snapshot unchanged, do not claim a v2 identity, and do not publish a journal-eligible completion.

Migration must be idempotent: reloading an already migrated session must not generate another ID. Existing unknown/unsupported session schemas must remain preserved and must not be rewritten by this migration.

Before implementation, verify that no external consumer depends on the old timestamp ID format. Search all reads/writes of `Tahouri_ActivitySession`, `session.id`, and any logs or UI that parse the ID.

## 6. Required tests before runtime implementation is accepted

### Generator tests

- `crypto.randomUUID()` path returns a correctly shaped UUID v4.
- `getRandomValues` fallback returns a correctly shaped UUID v4 with correct version/variant bits.
- Missing `crypto` and missing `getRandomValues` fail closed.
- `Math.random()` is never used.
- Deterministic injected random bytes make the fallback test reproducible.

### Lifecycle tests

- Same activity + same fixed millisecond + two fresh attempts => different IDs.
- Same activity + same fixed millisecond + two profiles => different IDs and isolated storage.
- Same active attempt + repeated `begin()` => same ID.
- Resume after reload => same ID.
- Capture before and after resume => same ID.
- Explicit restart after clear/completion => new ID.
- Failed persistence => no journal-eligible session.
- Legacy migration creates one v2 ID, preserves `legacyId`, and remains stable over repeated reloads.
- Failed legacy migration leaves the original stored snapshot byte-for-byte unchanged.
- Profile mismatch and unsupported schema remain rejected without deleting stored evidence.

### Completion boundary tests

After the identity generator and lifecycle tests pass, test the completion envelope at the central `ActivityLifecycle` boundary before the session is cleared. Verify that every supported engine path uses the active persisted session ID and duplicate terminal delivery cannot create a second accepted completion.

The broader producer, duplicate/re-entrancy, and dataset fan-out acceptance matrix remains mandatory. Generator tests alone do not authorize Change Journal integration.

## 7. Scope and safety boundaries

This proposal does not change `ActivitySessionManager`, engine code, storage writers, sync APIs, Worker, D1, production data, or deployment.

Implementation sequence, only after design approval:

1. Trace all session ID consumers and all `begin()` callers.
2. Add a standalone UUID generator and deterministic unit tests without wiring it into runtime.
3. Add migration and lifecycle tests using synthetic profiles and isolated storage.
4. Review the test results and approve the runtime change separately.
5. Only later, after engine completion publisher and duplicate-delivery gates pass, design Change Journal integration.

**Acceptance rule:** no insecure fallback; no ID rotation on resume; no profile cross-load; no journal publication without a validated persisted identity.

## 9. Persistence and migration boundary findings — 2026-11-27

A second source inspection of the active ActivitySessionManager, ActivityManager, SaveManager, and ProfileContext found additional implementation blockers. These are observations of current code, not runtime changes.

### 9.1 Session persistence failure is not fail-closed today

- ActivitySessionManager.save(session) returns the boolean result of SaveManager.save(...).
- ActivitySessionManager.begin(activity) assigns this.currentSession = session, calls this.save(session), but does not check the returned boolean. It then sets gameplayActive = true and returns the in-memory session.
- ActivityManager.start() only checks whether begin() returned a truthy session. It therefore proceeds to engine startup even if localStorage.setItem failed and the session was never persisted.

**Required correction before runtime acceptance:** begin() must not report a resumable/journal-eligible session unless the profile-scoped snapshot was successfully persisted and can be validated. The failure path must restore a safe in-memory state and return a clear failure result. The product decision about whether gameplay is blocked or allowed in a clearly non-resumable local-only mode remains open; current code does not implement either policy safely for journal publication.

### 9.2 Unsupported/legacy snapshots can be overwritten by a fresh start

- validateSession() accepts only the current manager version and exactly SCHEMA_VERSION (currently 1). An unknown schema is rejected by load(); load() leaves the stored key intact but clears currentSession.
- On a normal fresh activity start, ActivityManager.start() calls load(). If the snapshot is rejected, existing is null and startup continues toward begin().
- begin() calls load() again; if it is still rejected, it creates a new session and calls save() using the same profile-scoped Tahouri_ActivitySession key.
- save() writes through SaveManager.save() to that same key. Thus an unsupported or unrecognized snapshot can be overwritten by a fresh session even though load() itself did not delete it.

**Required correction before migration acceptance:** distinguish “no saved session” from “saved but invalid/unsupported session.” Do not overwrite the latter automatically. A migration must inspect and preserve the original raw stored snapshot, and only replace it after successful validation, secure ID generation, and successful persistence of the migrated value. On failure, the original raw value must remain byte-for-byte unchanged.

### 9.3 Migration order and schema compatibility

The current load() calls validateSession() before assigning currentSession, and the validator rejects schema versions other than the current one. A v1-to-v2 migrator therefore has to run at a carefully defined boundary before the v2-only validator, while still validating the legacy v1 structure and active profile. The migration must not turn arbitrary unsupported schemas into v2 sessions.

The current SaveManager.load() parses JSON and returns an object, but it does not expose the original raw serialized value. A byte-for-byte preservation assertion will need a test adapter around the underlying storage or a deliberately scoped raw-read path; it must not be implemented by weakening the shared SaveManager contract without separate review.

### 9.4 Confirmed profile and storage boundaries

- ProfileContext.key("Tahouri_ActivitySession") appends the active student ID and returns null when no active student profile exists.
- ActivitySessionManager.storageKey() uses that profile-scoped helper.
- SaveManager.save() catches storage exceptions and returns false; SaveManager.remove() also returns a boolean.
- The current ActivitySessionManager.begin() does not verify that profileId is non-empty before constructing the session, so a missing profile context can still create an in-memory session object even though the profile-scoped storage key is unavailable.

### 9.5 Remaining search limitation

The inspected source confirms the above direct call paths and behaviors. It does not complete a repository-wide inventory of every currentSession/session.id consumer, every Tahouri_ActivitySession read/write, or every caller of begin(). GitHub code-search queries returned no indexed matches in this pass, so no claim of exhaustive consumer tracing is made. That inventory remains a prerequisite to runtime changes.


## 10. Recommended startup failure policy — pending approval — 2026-11-27

### Recommendation: fail closed when a durable session cannot be established

For the first runtime correction, recommend that a fresh activity must not enter its engine unless all of the following are true:

1. A valid active student profile is available.
2. A profile-scoped session storage key is available.
3. A cryptographically secure session UUID has been generated.
4. The session snapshot has been successfully persisted and read back/validated.

If any condition fails, `ActivitySessionManager.begin()` should clear any partially assigned in-memory session state, leave existing stored bytes untouched, and return `null` with a diagnostic reason. `ActivityManager.start()` already treats a null result from `begin()` as a startup failure: it clears the provisional current activity/history and returns before resolving or starting the engine. This makes fail-closed behavior the smallest compatible correction; no new fallback mode or architecture is required.

Do not silently continue in a non-resumable mode in this first correction. Such a mode would need explicit product behavior, clear UI messaging, and a rule that the resulting activity completion is never eligible for cross-device journal publication. That is a separate design decision.

### Required safeguards before implementing this recommendation

- Preserve an existing raw session snapshot when its schema/profile/version is unsupported; never overwrite it as a side effect of starting another activity.
- Distinguish an absent key from a present but invalid/unsupported key. The latter must stop automatic fresh-session creation and surface a recoverable diagnostic path.
- Verify a successful write against the exact profile-scoped key before publishing `currentSession` as active.
- Ensure a missing profile or key returns `null` before mutating gameplay state.
- Keep the resume path stable: a successful resumed session keeps its existing ID and is not assigned a new UUID.

### Scope status

This is a recommendation for review, not an approved runtime change. No production/runtime files, storage schema, student records, sync API, Worker, D1, or deployment were modified. Runtime implementation remains gated on approval of this policy and completion of the session consumer/caller inventory.

## 10. Recommended persistence policy — proposal for review

Based on the three reproduced diagnostics and the current caller contract, the safest default is **strict fail-closed startup** until an explicit local-only mode is designed and tested. This is a recommendation, not an approved runtime change.

### Required begin() contract

1. Resolve both the active profile ID and profile-scoped storage key before constructing a session. If either is absent or inconsistent, return failure without changing currentSession, gameplayActive, or the document's playing class.
2. Inspect whether the storage key already exists before creating a new session. Distinguish:
   - key absent: a fresh session may be created;
   - valid supported session: follow the explicit resume/restart rules;
   - malformed, unsupported, or unrecognized stored value: preserve it and refuse automatic replacement;
   - read/parse/storage error: treat as an error, not as an empty slot.
3. Generate the secure UUID and build the candidate session without publishing it as current.
4. Persist the candidate. Only after successful persistence and read-back validation may it become currentSession and allow begin() to return a truthy resumable session.
5. If persistence or read-back validation fails, preserve the prior in-memory state and return failure. The existing ActivityManager.start() already aborts when begin() returns falsy, so this can enforce strict behavior without introducing a second startup mode.
6. Do not automatically clear or overwrite unknown snapshots. A future explicit recovery/reset action must be separately designed, clearly explained to the user, and tested against profile isolation.

### Storage API gap

SaveManager.load() returns null both when a key is absent and when reading/parsing fails. SaveManager.exists() can distinguish a present key in normal conditions, but it also returns false on storage exceptions. Before implementing migration, introduce a session-scoped read result that distinguishes missing, valid, invalid-json, unsupported-schema, and storage-error, without exposing raw student data in logs. Do not globally change SaveManager semantics as part of this narrowly scoped work unless a separate compatibility audit justifies it.

### Mandatory acceptance tests before runtime wiring

- begin() with no profile: returns failure and changes no runtime flags.
- begin() with unavailable storage: returns failure, does not set currentSession, and does not allow engine.start().
- A successful save followed by a failed read-back: returns failure and does not allow engine.start().
- Existing malformed JSON: remains byte-for-byte unchanged after attempted fresh start.
- Existing unsupported schema: remains byte-for-byte unchanged after attempted fresh start.
- Existing valid v1 session: migration either persists one valid v2 identity before resume, or leaves the original snapshot unchanged on any failure.
- Explicit fresh restart after a valid old session: only clears/replaces it after the restart path has positively identified and accepted that valid session.
- Verify ActivityManager.start() does not call the engine when begin() fails.
- Verify successful begin() persists before engine startup and activityReady reuses the same ID.
- Verify all failure paths restore prior currentSession, gameplayActive, and CSS state.

**Gate:** no production runtime wiring until these tests pass, all begin() callers and currentSession/session.id consumers are traced on this exact branch, and the user approves the selected startup/recovery policy.

## 10. Migration prototype review — compatibility boundary

The isolated migrator test suite is not a runtime-ready migration. Source inspection confirms the active manager currently declares both `VERSION: "1.9"` and `SCHEMA_VERSION: 1`; its validator rejects any non-1 schema. The prototype emits `schemaVersion: 2` while preserving the old `version: "1.9"`. Therefore, the current runtime would reject the migrated record unless a coordinated runtime version/schema change and migration-aware load path are implemented.

Before any runtime wiring:
- Define the next manager version and schema compatibility policy explicitly.
- Make the migration's legacy validator match every branch of the real `validateSession()`, including engine-specific state requirements, not merely generic object/profile checks.
- Test all currently supported session engine types and profile scoping against real v1-shaped fixtures.
- Verify that the runtime can load the migrated schema and that a failed migration preserves the original raw bytes.
- Keep the migration prototype isolated until those gates and the user's separate runtime approval are complete.

The current prototype's rollback attempts to rewrite and verify the original raw string after a candidate write/read-back failure. If the storage backend is unavailable for both candidate and rollback operations, preservation cannot be guaranteed; it reports `rollback-failed` rather than claiming success. Production integration must use a safer commit strategy or a storage transaction/backup mechanism that makes the original recoverable without relying on a second successful write.

## 12. Resume transaction finding — active runtime source

A further source-level blocker was confirmed in `ActivitySessionManager.resume()`:

- It publishes the attempted snapshot to `currentSession` before calling `restoreEngine()`.
- If restore returns false or throws, `finally` clears only `restoringSession`; it does not restore the prior `currentSession`.
- On successful restore it changes `session.status` to `active`, calls `save(session)`, but ignores a false save result and still reports resume success.
- Therefore UI/engine restore may succeed while the persisted record remains resumable, or a failed restore may leave a failed target published in memory.

Required acceptance cases before runtime integration:
1. Restore returns false: prior currentSession and persisted raw snapshot remain unchanged.
2. Restore throws: same rollback, with restoringSession reset.
3. Restore succeeds but persistence fails: resume must not report committed success; define and test rollback of engine/UI or a recoverable pending state.
4. Successful restore + verified save: currentSession and persisted status both become active.
5. Matching snapshot must be tested through manager validation and manager restore dispatch, not only its engine methods.

This is a confirmed source finding, not yet a runtime patch. No runtime, Worker, D1, or production files were changed.

## 16. Per-engine restore side-effect inventory and prepare/commit boundary — 2026-11-28

This section translates the R4–R9 diagnostics into an implementation boundary. It is a source inventory of the active `engine/activity/activitySessionManager.js` restore branches, not a runtime change.

### Side-effect inventory

| Restore family | Live engine mutations before commit | Other visible/global mutations before commit | Existing local rollback coverage |
|---|---|---|---|
| Dictation | `activity`, `content`, `state`, `runToken`, `finishAuthorized`; `restoreSession()` mutates the engine | `activateRestoredActivity()`; `DictationScreen.render()` changes the live screen | Engine fields restored on false/throw; global activity and rendered UI are not rolled back by the branch |
| WordPuzzle | `activity`, `state`, `round` through `restoreSession()` | `activateRestoredActivity()` | Engine fields restored on false/throw; no staged UI boundary |
| Quiz | `activity`, `questions`, `currentQuestion`, `state`; ScoreManager counters | `QuizScreen.reset/show()` writes live `#app`; then ActivityManager.currentActivity, ActivityState and body class | Engine, score, screen lock and app markup restored for local false/throw; successful restore followed by save failure is not rolled back |
| Memory | activity, cards, first/second card, board lock, matched pairs, moves, total pairs, finished; ScoreManager counters | `MemoryScreen.show()` writes live `#app`; then ActivityManager.currentActivity, ActivityState and body class | Engine, score and app markup restored when render rejects/throws; successful restore followed by save failure is not rolled back |
| Puzzle/Jigsaw | activity, state, puzzle, questions, current question, items, answer, moves, transition/check flags and request IDs | Jigsaw facade states; `PuzzleScreen.show()` writes live `#app`; then ActivityManager.currentActivity, ActivityState and body class | Engine, score, Jigsaw facade and app markup restored for local false/throw; successful restore followed by save failure is not rolled back |
| Classification | `activityData`, `content`, `handler`, `state` via `restoreSession()` | ActivityManager.currentActivity, ActivityState, body class; ClassificationScreen currentActivity/currentState/lastMessage and rendered screen | Engine fields restored for false/throw; screen/global activity changes are not transactionally reverted after later persistence failure |

### Shared commit-time effects

After `restoreEngine()` returns true, the active manager currently:
1. changes the candidate session status to `active`;
2. calls `save(session)` without checking its return value or reading the persisted value back;
3. sets `gameplayActive` and the body `activity-playing` class;
4. installs the exit control;
5. emits `activityResumed`.

The restore branches themselves may already have published engine/UI/activity state before step 1. The exit control and event are therefore too late to define the transaction boundary; all preceding effects must be staged or recoverably isolated.

### Required adapter contract

A future implementation should use an explicit per-engine adapter with these conceptual operations:

- `capture()`: capture the exact pre-restore engine, score, screen, facade and activity-global state needed for rollback.
- `prepare(snapshot, detachedHost)`: validate and build the candidate engine state and screen output without mutating the live engine, live `#app`, ActivityManager, ActivityState, body classes, exit controls, or emitting events.
- `commitPrepared(prepared)`: publish the prepared engine and screen only after persistence has been written and read back successfully.
- `rollback(captured)`: restore all captured state if a commit-stage operation fails; return explicit per-subsystem failures rather than swallowing them.
- `dispose(prepared)`: release detached DOM/resources when preparation or persistence fails.

A prepared screen must be rendered into a detached host. Existing `QuizScreen.show`, `MemoryScreen.show`, `PuzzleScreen.show`, `DictationScreen.render`, and `ClassificationScreen.show` currently target live UI or global screen state; they cannot be called during preparation unless first adapted to accept an isolated render target and avoid global publication.

Engine preparation must not call a mutating `restoreSession()` on the live engine. Either each engine must expose a pure state builder, or the adapter must restore into an isolated engine instance with all dependencies explicitly bound. A shallow clone is not sufficient evidence of isolation where nested state, singleton providers, timers, event listeners, or closures may be shared.

### Commit ordering

The proposed ordering is:

1. Validate the resumable snapshot and resolve the profile-scoped persistence key.
2. Capture the currently visible/runtime state and exact persisted raw bytes.
3. Prepare the engine candidate and detached screen; verify the candidate without publishing it.
4. Persist the candidate active snapshot and read it back; require exact semantic equality and schema validity.
5. Publish engine state and prepared screen; publish ActivityManager/ActivityState/body class and gameplay state.
6. Install exit controls.
7. Emit `activityResumed` only after all prior commit steps succeed.
8. If any step after durable persistence fails, restore the exact prior raw bytes and verify the restoration, then roll back all published runtime/UI state. If either rollback cannot be verified, return an explicit `rollback-failed` state and retain recovery evidence; never report a clean resume.

The exact ordering of runtime publication versus durable write remains conditional on a successful staged adapter: no visible game may appear before the persisted active record is verified. The implementation must also prove that the commit publication operations are synchronous/non-throwing or have complete rollback coverage.

### Acceptance matrix for the adapter phase

For each of the six supported families (Quiz, Memory, Puzzle, Dictation, WordPuzzle, Classification), tests must prove:
- preparation leaves live engine/global/UI state byte-for-byte or semantically unchanged;
- preparation failure leaves the previous screen and session intact;
- persistence false, throw, malformed read-back, and read-back mismatch do not publish the prepared screen or active gameplay state;
- successful verified persistence publishes the expected engine state and screen exactly once;
- commit failure restores the previous engine, score, DOM, facades, ActivityManager, ActivityState, CSS, exit control and persisted raw snapshot;
- `activityResumed` is emitted exactly once on success and never on a failed attempt;
- rollback failure is surfaced with the failing subsystem and preserved recovery data.

MatchingEngine and CompositeActivityEngine remain explicitly unsupported until their manager validation, dispatch, and adapter contracts are independently implemented and tested.

**Implementation gate:** this inventory and contract are design-only. The next code task is to prototype one isolated adapter against one engine family and prove that preparation does not mutate live state. Do not edit the active manager or wire any adapter until the isolated proof and its failure tests pass, and the user explicitly approves runtime integration. No runtime, Worker, D1, or production files were changed.
